# Лабораторные по параллельному программированию

Решения всех шести заданий из [tasks.md](tasks.md). Используется OpenJDK 27.0.0, закреплённый в `mise.toml`. Внешних Java-зависимостей и сборочных фреймворков нет.

## Подготовка

Все команды выполнять из корня репозитория:

```sh
mise trust
mise install
mise exec -- ./build.sh
```

`build.sh` компилирует исходники из `src` в `build/classes`. Всё содержимое `build` исключено из Git.

## Запуск

`run.sh` сначала собирает программы, затем запускает выбранную лабораторную:

```sh
mise exec -- ./run.sh 1
mise exec -- ./run.sh 2
mise exec -- ./run.sh 3
mise exec -- ./run.sh 4
mise exec -- ./run.sh 5 examples/project 4
mise exec -- ./run.sh 6 examples/project 4
```

Первая лабораторная по умолчанию читает `input.txt`, остальные анализируют `examples/project`. Следующим аргументом можно указать другой файл или папку. Например, так можно проанализировать исходники самих лабораторных:

```sh
mise exec -- ./run.sh 3 src
```

У лабораторных 5 и 6 второй аргумент после папки задаёт положительное число потоков-исполнителей. По умолчанию используется количество доступных процессоров.

После сборки можно запускать программу напрямую, без повторной компиляции:

```sh
mise exec -- java -cp build/classes lab2.Main examples/project
```

## Что находится в каждой лабораторной

| № | Основной файл | Как выполняется работа |
|---|---|---|
| 1 | [WordCounter.java](src/lab1/WordCounter.java) | Regexp выделяет слова, `Map` считает повторения |
| 2 | [Main.java](src/lab2/Main.java) | Последовательный разбор Java-файлов |
| 3 | [Main.java](src/lab3/Main.java) | Отдельный `Thread` на файл, ожидание через `CountDownLatch`, объединение в главном потоке |
| 4 | [Main.java](src/lab4/Main.java) | Отдельный `Thread` на файл, изменение общего индекса под `ReentrantLock` |
| 5 | [Main.java](src/lab5/Main.java) | Фиксированный пул `ExecutorService`; сначала выдаются все задания, затем читаются все `Future` |
| 6 | [Main.java](src/lab6/Main.java) | Фиксированные исполнители, две `BlockingQueue`, сбор результатов и завершение через poison pill |

В лабораторных 3 и 4 используются виртуальные потоки Java. Каждый файл получает отдельный объект `Thread`, но JVM распределяет их по потокам ОС. Это позволяет выполнить условие задания и работать с проектом из тысяч файлов. В лабораторных 5 и 6 ограничено именно число исполнителей.

В лабораторной 6 очередь заданий ограничена числом исполнителей, а очередь результатов не ограничена. Главный поток сначала выдаёт все задания, поэтому исполнители должны иметь возможность складывать результаты до начала их чтения. Иначе две заполненные ограниченные очереди могут остановить программу. Ошибка обработки файла также передаётся как результат.

## Общая часть поискового робота

- [SourceFiles.java](src/common/SourceFiles.java) находит обычные `.java`-файлы внутри папки.
- [JavaSourceParser.java](src/common/JavaSourceParser.java) разбирает каждый файл через публичный Compiler Tree API из JDK. У каждого вызова собственные компилятор, `FileManager` и `JavacTask`.
- [ParsedSource.java](src/common/ParsedSource.java) хранит объявления типов и ссылки на их родителей для одного файла.
- [InheritanceIndex.java](src/common/InheritanceIndex.java) объединяет результаты, разрешает имена родителей и печатает отсортированный индекс.
- [WorkerCount.java](src/common/WorkerCount.java) проверяет число исполнителей для лабораторных 5 и 6.

Обработка файла и объединение индексов разделены, поэтому механизм многопоточности меняется без копирования парсера. В четвёртой лабораторной потоки объединяют результаты под блокировкой, в остальных — главный поток. Имена родителей разрешаются после сбора всех объявлений.

## Как читать результат

```text
demo.base.Base -> demo.app.Document
demo.base.Readable -> demo.base.Writable
demo.other.Base -> demo.app.Document.Nested
```

Слева находится родитель, справа — его непосредственные наследники. Тип без найденных наследников выводится с пустой правой частью. Одинаковые простые имена из разных пакетов имеют отдельные записи.

Учитываются явно написанные `extends` и `implements`, включая наследование интерфейсов, несколько интерфейсов, вложенные типы, generics и аннотации типов. Комментарии и строки не создают ложных связей. Неявное наследование от `Object`, `Enum` и `Record` не добавляется.

Анонимные классы не имеют самостоятельной записи. Для локальных классов в имя добавляется позиция в файле, чтобы одноимённые объявления в разных методах не объединялись. Именованные типы внутри анонимного класса также получают контекст с позицией этого класса.

Первая лабораторная считает словами последовательности Unicode-букв с комбинируемыми знаками. Цифры и знаки препинания служат разделителями. Регистр не учитывается; преобразование использует `Locale.ROOT`, независимо от языка системы.

## Ошибки и границы анализа

Проверяется синтаксис Java, но анализируемый проект не компилируется и не запускается. Не требуется устанавливать его зависимости. Синтаксическая ошибка, недоступный файл или неверный путь завершают программу с ненулевым кодом; частичный индекс при такой ошибке не печатается.

Разрешение имён учитывает объявления в выбранной папке, пакет, явные и wildcard-импорты, платформенные типы JDK и унаследованные вложенные типы. Если внешнего типа нет в исходниках и его имя нельзя однозначно восстановить, связь сохраняется под ключом `[unresolved ...]`, а в stderr выводится объяснение. Это синтаксический индекс, а не полная проверка типов javac: например, неоднозначный внешний wildcard-импорт требует исходников зависимости или семантического анализа с её classpath.

Для проекта с несколькими модулями и повторяющимися полными именами типов выбирайте папку одного модуля: повторные объявления одного полного имени объединяются. Пустая папка даёт пустой индекс.

## Проверки

```sh
mise exec -- ./test.sh
```

`IndexTest` проверяет ожидаемый индекс примера, пакеты, generics, аннотации, локальные и унаследованные вложенные классы, импорты и ошибки синтаксиса. `IntegrationTest` запускает реальные программы отдельными процессами: сравнивает пять вариантов индекса, проверяет 129 исходников, разные числа исполнителей, пустые папки, ошибки файлов и счётчик слов. Для каждого процесса установлен таймаут, который обнаруживает зависание.

Все временные файлы тестов создаются в `build` и удаляются после проверки. Подробности проверки на Spring Framework и команды для повторения находятся в [docs/verification.md](docs/verification.md).

Для разбора кода начните с первой лабораторной, затем второй и общей части парсера. После этого сравнивайте `Main.java` лабораторных 3–6: задача и результат одинаковые, меняется способ организации работы.
