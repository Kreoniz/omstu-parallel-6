# omstu-parallel-6

Работы по предмету "Параллельное программирование" за 6 семестр ОмГТУ.

Реализованы лабораторные № 2–6 из [tasks.md](tasks.md): обратный индекс наследования классов и интерфейсов Java с разными способами организации потоков. Лабораторная № 1 с регулярными выражениями уже сдана и здесь не реализуется.

Каждая работа самостоятельна: один `src/labN/Main.java` содержит собственные обход файлов, парсер Java, построение индекса и организацию обработки. Общих Java-классов, утилит и зависимостей между лабораторными нет. Повторение кода намеренное: любую работу можно изучать, собирать и сдавать отдельно.

## Запуск

Используется OpenJDK 27.0.0 из `mise.toml`. Все команды выполнять из корня репозитория:

```sh
mise trust
mise install
mise run lab2
mise run lab3
mise run lab4
mise run lab5
mise run lab6
```

Все команды `mise run lab2` … `mise run lab6` по умолчанию анализируют Spring Framework из `build/spring-framework`. При первом запуске выбранная задача скачивает исходники; остальные работы используют уже скачанную папку. Для другой папки:

```sh
mise run lab2 /путь/к/Java-проекту
mise run lab3 /путь/к/Java-проекту
mise run lab4 /путь/к/Java-проекту
mise run lab5 /путь/к/Java-проекту 4
mise run lab6 /путь/к/Java-проекту 4
```

У № 5 и № 6 второй аргумент — положительное количество рабочих потоков. Без него используется число процессоров, но не более четырёх. У № 2–4 допустим только путь к папке.

Небольшой пример доступен по явному пути: `mise run lab2 examples/project` (номер от 2 до 6).

`mise run` без имени задачи тоже запускает лабораторную № 2 на Spring. Перед запуском собирается только выбранная работа, в отдельную папку `build/labN`. Все команды определены в [mise.toml](mise.toml), список с описаниями доступен через `mise tasks`.

Для отдельной работы доступны `mise run build:lab3` и `mise run test:lab3` (номер от 2 до 6). `mise run build` собирает все работы, `mise run test` проверяет все работы. Скрипты `build.sh`, `run.sh` и `run-spring.sh` заменены задачами mise; в `test.sh` находятся только проверки.

`mise` выбирает JDK из раздела `[tools]`, а `mise run lab3` выполняет задачу `[tasks.lab3]`. Сначала запускается её зависимость `build:lab3`: `javac` переводит `Main.java` в байткод `.class` в `build/lab3`. Затем при необходимости скачивается Spring и команда `java -cp build/lab3 lab3.Main` запускает программу. `-cp` указывает папку с байткодом, `lab3.Main` — имя класса вместе с пакетом. `mise exec -- команда` просто выполняет произвольную команду с выбранным JDK. `test.sh` создаёт тестовые проекты, запускает программы и сравнивает вывод с ожидаемым.

Для сборки без исходников других лабораторных достаточно выбранного файла и JDK, например:

```sh
mise exec -- javac -encoding UTF-8 -d build/manual-lab6 src/lab6/Main.java
mise exec -- java -cp build/manual-lab6 lab6.Main
```

## Лабораторная № 2: последовательная обработка

Вся реализация находится в [src/lab2/Main.java](src/lab2/Main.java):

1. `findJavaFiles` обходит папку и находит `.java`-файлы через Stream API.
2. `buildIndex` использует парсер из JDK, находит `class`, `interface`, `extends` и `implements` и собирает `Map<String, Set<String>>` с помощью `getOrDefault()`.
3. `simpleTypeName` извлекает имя родителя, убирая параметры типов и квалификатор пакета.
4. `main` выводит индекс. `TreeMap` и `TreeSet` обеспечивают сортировку и отсутствие повторов.

Для примера результат такой:

```text
Attachment ->
Base -> Attachment, Document
Document -> FeaturedDocument
FeaturedDocument ->
Identifiable -> Document
Readable -> Writable
Writable -> Document
```

Слева родитель, справа его непосредственные наследники. Если наследников нет, правая часть пустая. Вложенные классы тоже обходятся. Слова `class` и `extends` в строках и комментариях не создают ложных связей.

В индексе используются простые имена: `demo.Base` выводится как `Base`. Одноимённые типы из разных пакетов или областей объединяются. Анонимные классы, enum и record не добавляются как отдельные записи; неявное наследование от `Object` не учитывается.

Программа разбирает синтаксис исходников; зависимости анализируемого проекта устанавливать не требуется. Пустая папка даёт пустой результат.

## Что объяснять на защите лабораторной № 2

### Зачем нужен обратный индекс

В исходниках связь записана от ребёнка к родителю: `class Document extends Base<String>`. Робот разворачивает её: `Base -> Document`. Ключ `Map` — имя родителя, значение `Set` — имена его непосредственных наследников. Интерфейсы обрабатываются так же: `implements Writable` даёт `Writable -> Document`.

Индекс не вычисляет всех потомков по цепочке: у `Base` в примере нет `FeaturedDocument`, потому что тот непосредственно наследуется от `Document`.

### Как читать Main.java

1. `main` проверяет аргументы, выбирает папку, получает список файлов, строит индекс и выводит его. Допустим один необязательный аргумент — путь.
2. `findJavaFiles` рекурсивно обходит папку через `Files.walk`. `filter` оставляет обычные `.java`-файлы, `sorted` задаёт порядок, `toList` собирает результат. `try` с ресурсами закрывает поток обхода файловой системы. Stream API здесь последовательный: отдельных рабочих потоков нет.
3. `buildIndex` получает компилятор через `ToolProvider`, открывает файловый менеджер и создаёт `JavacTask`. Вызывается только `parse()`: он строит синтаксическое дерево, но не компилирует анализируемый проект в `.class` и не разрешает его зависимости. Поэтому нужен JDK, а сборка самого Spring не нужна.
4. `TreeScanner` обходит дерево. Его `visitClass` вызывается и для классов, и для интерфейсов. Проверка `Tree.Kind` исключает enum и record; пустое имя исключает анонимные классы. Вызов `super.visitClass` продолжает обход, в том числе внутри вложенных классов.
5. `putIfAbsent(child, new TreeSet<>())` создаёт запись даже для типа без наследников. Родители берутся из `getExtendsClause()` и `getImplementsClause()`. У интерфейса список расширяемых интерфейсов представлен в API дерева через `getImplementsClause()`, хотя в исходнике написано `extends`.
6. `simpleTypeName` снимает параметры типов и аннотации типа, затем оставляет часть имени после последней точки: `sample.Parent<String>` превращается в `Parent`.

Парсер отличает объявления от строк и комментариев. Строка `"class Fake extends Wrong {}"` не создаёт класс `Fake` в индексе.

### Как работает getOrDefault

```java
Set<String> children = index.getOrDefault(parent, new TreeSet<>());
children.add(child);
index.put(parent, children);
```

Если родитель уже есть, получаем его существующий набор наследников. Если его нет, получаем новый пустой набор. `getOrDefault` сам не добавляет отсутствующий ключ в `Map`, поэтому после `add` нужен `put`. При существующем ключе набор уже изменился по ссылке, а повторный `put` просто сохраняет тот же объект.

`TreeMap` сортирует родителей, `TreeSet` сортирует наследников и убирает повторы. Эти коллекции не обеспечивают синхронизацию; во второй лабораторной доступ к ним идёт из одного потока.

### Короткий рассказ о работе

«Программа рекурсивно находит Java-файлы и разбирает их парсером JDK. Я обхожу синтаксическое дерево, нахожу объявления классов и интерфейсов и для каждого явно указанного родителя добавляю имя ребёнка в обратный индекс. Индекс хранится в Map, значения получаю через getOrDefault. Для сортировки и удаления повторов использую TreeMap и TreeSet. После обработки всех файлов вывожу непосредственных наследников каждого типа».

Для объяснения на небольшом примере запустить `mise run lab2 examples/project` и сопоставить вывод с файлами в `examples/project`. Для демонстрации на большом проекте запустить `mise run lab2`: команда анализирует Spring Framework. Проверка второй работы: `mise run test:lab2`.

## Лабораторная № 3: независимые потоки

Реализация: [src/lab3/Main.java](src/lab3/Main.java).

На каждый файл создаётся отдельный виртуальный `Thread`. Виртуальные потоки позволяют запустить обработку тысяч файлов без создания такого же количества потоков ОС. Пул заданий в этой работе не используется.

Каждый поток строит собственный индекс и записывает результат в свою ячейку массива. Рабочие потоки не читают результаты друг друга и не изменяют общий индекс. Основной поток ждёт `CountDownLatch.await()`, проверяет ошибки и печатает отдельный индекс каждого файла с заголовком `FILE путь`. Общий индекс намеренно не формируется.

`countDown()` находится в `finally`, поэтому обычная ошибка разбора не оставляет основной поток в вечном ожидании. Массив результатов читается только после `await()`; строки разных файлов не перемешиваются.

### Main-optimized: пакетный разбор

Самостоятельная реализация находится рядом в [src/lab3/Main-optimized.java](src/lab3/Main-optimized.java). Java-класс называется `MainOptimized` и не объявлен `public`, поэтому имя файла может содержать запрошенный дефис.

```sh
mise run lab3-optimized
mise run lab3-optimized examples/project 2
mise run lab3-optimized build/spring-framework 4
mise run test:lab3-optimized
```

По умолчанию анализируется Spring. Число исполнителей равно количеству доступных JVM процессоров, но не превышает число файлов; его можно задать вторым аргументом после пути. Файлы делятся на последовательные пакеты примерно одинакового размера. Каждый пакет получает свой обычный `Thread`, один `JavacTask` и один файловый менеджер. У каждого файла остаётся собственный индекс. После ожидания через `CountDownLatch` результаты выводятся в том же порядке и формате, что у исходной № 3.

Это отдельный эксперимент с производительностью: он использует поток на пакет. Требование задания № 3 «поток на каждый файл» по-прежнему выполняет исходный `Main.java`.

Для сравнения без вывода индекса:

```sh
mise run lab3 --benchmark
mise run lab3-optimized --benchmark
mise run bench:lab3
mise run bench:lab3 build/spring-framework 4
```

`--benchmark` ставится перед путём и печатает только число файлов, число рабочих потоков и `index_ms`. Замер начинается перед созданием потоков и заканчивается после ожидания результатов: включает инициализацию парсеров, разбор и построение индексов, организацию потоков и ожидание. Обход папки, компиляция самого анализатора и вывод результатов не измеряются. `bench:lab3` выполняет три последовательные пары запусков исходного и оптимизированного вариантов; каждый запуск использует новую JVM. Общего Java-кода с исходной работой нет.

Проверено 24.10.2026 на OpenJDK 27 и Spring v7.0.9 (9 210 файлов): вывод двух вариантов совпал побайтно. Медиана трёх замеров `index_ms`: исходный вариант — 5 867,766 мс, пакетный с 16 исполнителями — 2 686,798 мс, ускорение около 2,18 раза на этой машине. Результат зависит от проекта и доступных ресурсов.

## Лабораторная № 4: единый индекс и ReentrantLock

Реализация: [src/lab4/Main.java](src/lab4/Main.java).

Каждый файл обрабатывается своим виртуальным `Thread`. Поток разбирает файл в локальный индекс, затем захватывает `ReentrantLock` и добавляет результат в единую `Map`. Чтение файла и работа парсера выполняются вне блокировки.

Блокировка защищает всю операцию объединения: получение набора наследников, добавление элементов и сохранение значения. `unlock()` находится в `finally`. Основной поток дожидается всех исполнителей через `CountDownLatch`, проверяет ошибки и только затем выводит общий индекс.

## Лабораторная № 5: ExecutorService и Future

Реализация: [src/lab5/Main.java](src/lab5/Main.java).

`Executors.newFixedThreadPool` создаёт пул с фиксированным количеством рабочих потоков. Для каждого файла отправляется задание, возвращающее собственную `Map`. Все полученные `Future` собираются в список.

Отправка заданий и чтение результатов находятся в двух отдельных циклах: первый вызывает `submit()` для всех файлов, второй вызывает `get()` и объединяет результаты. Общий индекс изменяет только основной поток, поэтому блокировка ему не нужна. `try` с ресурсами закрывает `ExecutorService` и дожидается завершения его работы.

## Лабораторная № 6: BlockingQueue и Map-Reduce

Реализация: [src/lab6/Main.java](src/lab6/Main.java).

Создаются две `BlockingQueue` и фиксированное число обычных потоков-исполнителей:

1. Основной поток помещает задания с путями в первую очередь.
2. Каждый исполнитель извлекает задание, строит локальный индекс (Map) и отправляет результат во вторую очередь.
3. Основной поток забирает столько результатов, сколько было файлов, и объединяет их в единый индекс (Reduce).
4. По одному poison pill на исполнителя отправляются после всех заданий. Получив его, исполнитель завершается; основной поток вызывает `join()` для всех исполнителей.

Обе очереди — `LinkedBlockingQueue` без заданного ограничения ёмкости: основной поток может выдать все задания, прежде чем начнёт принимать результаты, без взаимной блокировки двух заполненных очередей. Ошибка разбора тоже передаётся как результат; основной поток получает остальные результаты и завершает программу с ошибкой без печати неполного индекса.

В № 3–6 у каждого разбора собственные `JavacTask`, файловый менеджер и локальная `Map`. Ошибки синтаксиса исходников приводят к ненулевому коду завершения.
